## 典型报错与解决

### 1. uv 自动下载 Python 卡死（2026-09-24，第 1 课段 1）

- 现象：`uv python pin 3.12` 触发的 cpython-3.12.14 下载（32.6MiB，来自 GitHub）长时间无进展。
- 原因：GitHub 直连极慢（HEAD 请求都要 5s），uv 下载无进展即卡死；ghproxy 类加速站已失效。
- 解决：从南京大学镜像站
  `mirror.nju.edu.cn/github-release/astral-sh/python-build-standalone/LatestRelease/`
  下载同名 `cpython-3.12.14+20260901-x86_64-unknown-linux-gnu-install_only.tar.gz`，
  解压到 `~/.local/share/uv/python/<同名目录>/`（uv 未自动识别），再用其中解释器显式
  `uv venv --python <解释器路径>` 创建 `.venv`。
- 学到什么：① 镜像站（NJU/TUNA）是国内开发的基础生存技能；② uv 优先使用项目内现成的
  `.venv`，解释器怎么来的它不关心；③ `uv python install <本地文件>` 在 uv 0.12 不被支持。

### 2. PyPI 官方源慢

- 现象：pypi.org 响应 ~5s/请求。
- 解决：`~/.config/uv/uv.toml` 配置清华 TUNA 镜像（`[[index]] url=... default=true`），降至 ~0.5s。
- 学到什么：uv 的用户级配置文件一次性惠及所有项目；删除即恢复官方源。

### 3. 项目目录整体移动后 .venv 失效（2026-09-25）

- 现象背景：把项目从 `~/ln_rebuild_zcode/nanobot-st` 移到 `~/ln_rebuild_zcode/nanobot/nanobot-st`。
- 原因：虚拟环境内部（pyvenv.cfg、bin/ 脚本的 shebang）记录的是**绝对路径**，目录一挪全部失效。
- 解决：`rm -rf .venv && uv venv --python <解释器> && uv sync` 一分钟内重建（uv 缓存让重装很快）。
- 学到什么：**虚拟环境是"一次性餐具"，不是资产**——删了重建即可，永远不要挪、不要提交进 git。真正的资产是 pyproject.toml + uv.lock。

## 重要误解与澄清

### 1. "为什么 nanobot-st 里还有一个 nanobot_st？能不能合并成一层？"（2026-09-25，学生提问）

- 学生直觉：两层同名目录看着冗余。
- 澄清：外层是**项目/仓库**（pyproject.toml、tests、tutorial、.venv、.git 的家），内层是
  **Python 包**（被 import 的代码的家）。不能合并的硬理由：
  ① Python 包名不允许连字符（`import nanobot-st` 语法错误），包目录必须叫 `nanobot_st`；
  ② 若包=项目根，tests/tutorial/.venv 都会变成包的子模块，污染导入与发布边界。
- 佐证：原项目 nanobot 就是同样结构（仓库 `nanobot/` 套包 `nanobot/`），即 Python 标准 flat layout。
- 学生已理解认可。（此问答本身就是"项目 ≠ 包"这一 Python 工程基本认知的建立过程。）

## 学生的高价值理解

### 1. 对第 4 课重构本质的概括（2026-09-26）

- 学生原话（整理版）：工具注册表本质上是**把 if/else 的映射关系内化到了一个 dict 当中**；
  但注册仍依赖 `__init__.py` 里的逐个 `register()`，而非自动扫描。
- 评价：完全准确。这正是一次重构的两面——分发自动化（dict 查找 + 多态）、登记手工化。
- 延伸留档：原项目 `ToolLoader.discover()` 用 pkgutil 扫描 + 反射自动发现全部工具子类（含
  entry_points 外部插件）。教学项目暂不实现：三个工具手写三行登记尚不构成痛点，等工具数量
  增长后再让"登记行之痛"推动自动发现——符合"需求先于设计"。
