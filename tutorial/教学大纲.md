# 教学大纲

> 重建项目：`nanobot-st`（Python 3.11+）。目标：从"一个会问 AI 的脚本"逐步演化成一个小而完整的个人 AI agent。
> 规划 16 课主线（+若干可选扩展课）。本文件同时是进度表：完成后把 `[ ]` 改 `[x]`。
> 硬约束：任何时候只推进当前课；每课结束项目必须可运行、测试通过；抽象只在痛点出现后引入。

## 课程主线总览

```text
第 1 课  单问单答脚本            —— 打通"消息进、回答出"
第 2 课  多轮对话(内存)          —— 消息列表即状态；转入异步
第 3 课  第一个工具              —— tool call 循环(全课程核心)
第 4 课  工具注册表              —— 第一次由痛点驱动的抽象
第 5 课  会话持久化(JSONL)       —— 重启不失忆
第 6 课  系统提示词与上下文管理  —— 人设 + 截断保配对
第 7 课  流式输出                —— 回调 + 异步迭代器
第 8 课  重试与容错              —— 错误分类 + 指数退避
第 9 课  交互终端与多会话        —— 像"产品"一样使用
第 10 课 文件工具与工作区        —— AI 能读写文件
第 11 课 shell 工具              —— AI 能跑命令；安全边界
第 12 课 子代理                  —— 并发与上下文隔离
第 13 课 长期记忆                —— 跨会话记住用户
第 14 课 配置系统                —— 告别硬编码
第 15 课 HTTP API 服务化         —— 从脚本到服务
第 16 课 Provider 抽象与 fallback —— 第二个模型供应商倒逼重构
```

## 第 1 课：第一次对话——写一个会问 AI 的脚本

### 背景
还没有任何项目。我们只有一个愿望：在终端里向 AI 提一个问题，拿到它的回答。

### 本课需求
一个最小脚本：输入一个问题字符串，调用大模型 API，打印回答。

### 任务
- [ ] 从零搭建项目：git init、uv/venv 环境、VS Code 配置、pytest 就绪
- [ ] 安装 openai SDK，理解 OpenAI 兼容 API 生态（api_key/base_url/model）
- [ ] 实现 `ask_question(client, question) -> str`：组装 messages、发请求、取回答
- [ ] 用手写的 FakeClient 注入测试（不花真钱）：验证请求格式与响应解析
- [ ] 提供命令行真实运行入口（读环境变量里的 key/model）

### 主要技术点
项目工程化（venv/uv、pyproject、pytest、VS Code Testing 面板）；chat completions 消息格式（role/content）；依赖注入雏形（函数收 client 参数）；TDD 首循环。

### 预计影响
新建 `nanobot_st/chat.py`、`tests/test_chat.py`、`pyproject.toml`。

### 与上一课的关系
课程起点。

### 完成标准
测试通过；用真实 key 跑一次得到回答；学生能口头复述"一条消息长什么样、响应里答案在哪"；完成首次 commit。

## 第 2 课：别忘了我——多轮对话与内存会话

### 背景
第 1 课的助手是"金鱼"：每次调用只带一条消息，追问"那为什么呢"它不知道"那"指什么。

### 本课需求
连续对话：把历史消息一路带上，AI 记得上文。

### 任务
- [ ] 从同步迁移到异步（async/await）：讲清"等网络也是等"与事件循环直觉
- [ ] 引入 `Session`（内存版）：一个会话 = 一个消息列表
- [ ] 改造调用：`messages = 历史 + 新问题`，回答 append 回历史
- [ ] 最朴素的终端聊天循环（while + input）验证效果
- [ ] 测试：两轮对话，FakeClient 验证第二轮请求确实带上了第一轮的问答

### 主要技术点
async/await 基础（大白话→例子→代码）；"状态"的第一形态（内存列表）；pytest-asyncio。

### 预计影响
改造 `chat.py`（异步化）；新增 `nanobot_st/session.py`；`tests/test_session.py`。

### 与上一课的关系
第 1 课每次调用都是独立的——因为 messages 每次都是新建的；让消息列表活得比一次调用久，就是会话。

### 完成标准
测试通过；终端里连续追问能承上启下；能解释"AI 的记忆其实就是我们每次重发的消息列表"。

## 第 3 课：给 AI 一双手——第一个工具调用

### 背景
问它"现在几点"，它只能道歉。模型被关在 API 后面，碰不到现实世界。

### 本课需求
让 AI 能调用我们提供的一个函数（获取当前时间），拿到结果再作答。

### 任务
- [ ] 定义 `get_time` 工具：函数 + JSON Schema 描述（名字/描述/参数）
- [ ] 请求时携带 tools 参数
- [ ] 解析响应中的 `tool_calls`，执行对应函数，把结果包成 `role:"tool"` 消息回填
- [ ] 手写 while 工具循环：模型要工具就给、给完再问、直到 `finish_reason=stop`
- [ ] 测试：FakeClient 依次返回"要工具"→"最终回答"两个预设响应，验证循环与消息序列

### 主要技术点
JSON Schema；`finish_reason`（stop/tool_calls）作为循环方向盘；`role:"tool"` 与 `tool_call_id` 配对；while 循环里的状态累积。

### 预计影响
新增 `nanobot_st/tools_builtin.py`（暂名，两个工具前不抽象）；改造 `chat.py` 的调用逻辑。

### 与上一课的关系
第 2 课的调用链是"问→答"一条直线；本课在中间长出一个"环"（loop），这是 agent 与聊天机器人的分水岭。

### 完成标准
测试通过；真实运行问"现在几点"得到正确时间；能白板画出"用户问题→tool_calls→执行→回填→最终回答"的消息序列。

## 第 4 课：工具多起来——工具注册表

### 背景
想加第二个工具（简单计算器/随机数）。第 3 课的代码里，工具的定义、schema、if/else 分发都写死在一起，每加一个工具要改三处。

### 本课需求
加两个新工具，且加工具的成本降到"只写一个类"。

### 任务
- [ ] 引入 `Tool` 基类（第一个抽象类！name/description/parameters/execute）
- [ ] 引入 `ToolRegistry`：注册、按名查找、统一产出 tools 列表
- [ ] 迁移第 3 课的 get_time 与新工具到新体系，删除 if/else
- [ ] 支持一次响应里的多个 tool_calls 依次执行
- [ ] 测试：注册后 schema 正确生成；多工具调用全部执行并按序回填

### 主要技术点
抽象基类与多态（由重复痛点引出，不贴标签）；注册表模式；`to_schema()` 自动生成；"开闭"的直觉（对扩展开放=加类不改主流程）。

### 预计影响
新增 `nanobot_st/tools/`（base.py + 具体工具）；改造 `chat.py` 用注册表。

### 与上一课的关系
第 3 课证明了工具循环可行；本课是第一次真正意义上的重构：行为不变、结构变好。

### 完成标准
测试通过；新加一个工具只新建一个文件；能说出"抽象不是设计出来的，是被三处重复逼出来的"。

## 第 5 课：重启不失忆——会话持久化

### 背景
聊了一下午，Ctrl+C 退出再启动，全忘了。内存里的 Session 随进程消亡。

### 本课需求
会话保存到磁盘，重启后接着聊。

### 任务
- [ ] 设计 JSONL 文件格式（首行元数据 + 每行一条消息）
- [ ] 实现 save：追加/原子写（临时文件 + rename 的直觉讲解）
- [ ] 实现 load：启动时按会话名恢复
- [ ] 测试：写→读→继续对话，历史完整；损坏行跳过不崩
- [ ] （对照小节）原项目怎么做：LRU、checkpoint、filelock——为什么教学版不做

### 主要技术点
JSON 序列化边界（datetime 等）；JSONL vs JSON 的取舍；原子写；`~/.nanobot_st/` 数据目录约定；路径库 pathlib。

### 预计影响
新增 `nanobot_st/storage.py`（或 session.py 扩展）；Session 增加会话名/路径。

### 与上一课的关系
第 2 课的内存 Session 到此完成形态：同一个对象，换了保存地点。

### 完成标准
测试通过；重启程序能续聊；能解释"为什么一行一条消息而不是一个大 JSON"。

## 第 6 课：助手的人格——系统提示词与上下文管理

### 背景
每次都要先说"请用中文回答，你是我严谨的工作助手"；且聊得久了历史越来越长，又贵又可能超限。

### 本课需求
固定人设（不用每次交代）+ 历史长度控制（不超限）。

### 任务
- [ ] 引入 system 消息与 `ContextBuilder`：system prompt = 人设 + 规则
- [ ] token 概念（为什么按 token 计费/限长；字符数/4 粗估）
- [ ] 截断策略：保留最近 N 条，且**不拆散 tool_call/tool 配对**（不变量测试）
- [ ] 测试：请求首条恒为 system；超长历史被截断后消息序列仍然合法

### 主要技术点
system/user/assistant/tool 四种角色的完整图景；上下文窗口；截断的不变量（配对完整、首条 system）；（延伸）原项目的摘要压缩思路。

### 预计影响
新增 `nanobot_st/context.py`；`chat.py` 组装逻辑移交 ContextBuilder。

### 与上一课的关系
持久化解决"纵向"的时间问题；本课解决"横向"的内容问题——发出去的上下文到底装什么。

### 完成标准
测试通过；人设稳定生效；能解释截断为什么必须保配对。

## 第 7 课：别让我干等——流式输出

### 背景
长回答要干等 20 秒才整段蹦出来。体验差，也无法做"正在输入"的反馈。

### 本课需求
回答边生成边显示（打字机效果）。

### 任务
- [ ] openai SDK 流式接口：`stream=True`、`async for chunk`
- [ ] 回调设计：`on_content_delta(text)` 逐段交出（不用回调地狱，讲清控制反转直觉）
- [ ] 终端打字机打印；非流式路径保留（工具循环里两种响应统一收尾）
- [ ] 测试：FakeClient 产出多个 chunk，验证回调收到的文本顺序与聚合结果一致

### 主要技术点
异步迭代器（async for）；chunk 增量与聚合（delta vs 全文）；回调/钩子的直觉；（对照）原项目的 AgentHook/事件旁路。

### 预计影响
`chat.py` 出现流式分支；新增流式相关测试。

### 与上一课的关系
前六课的数据流都是"批处理"式的；本课第一次把"过程"本身当数据（增量）交出去。

### 完成标准
测试通过；真实运行可见逐字输出；能解释"为什么工具循环里最终消息要聚合后再入库"。

## 第 8 课：网络总不给力——重试与容错

### 背景
深夜跑长任务，一次 429/超时就整个崩掉，前面全白聊。

### 本课需求
可恢复的失败自动重试；不可恢复的失败给出人话报错。

### 任务
- [ ] 认识异常分类：网络/超时/限流(429)/鉴权(401)/内容超长——哪些值得重试
- [ ] 指数退避实现（1s/2s/4s，最多 3 次）
- [ ] 流式已输出后不重试的直觉（避免重复输出）
- [ ] 测试：FakeClient 前两次抛超时第三次成功——验证重试次数与最终成功；401 不重试
- [ ] （对照小节）原项目的 Retry-After/熔断/流恢复

### 主要技术点
异常层次；重试的适用边界；时间函数的可测试性（注入 sleep）；日志的基本用法（logging 替代 print 的时机）。

### 预计影响
新增 `nanobot_st/retry.py`；`chat.py` 调用包上重试。

### 与上一课的关系
流式让"长回答"体验变好；重试让"长会话"活得更久——都是可靠性演化。

### 完成标准
测试通过；能说出"重试只该用在幂等且瞬时的失败上"。

## 第 9 课：像样的助手——交互终端与多会话

### 背景
第 2 课的 while+input 太糙：没有退出命令、想开新话题得换整个数据目录、会话名靠手改代码。

### 本课需求
一个体面的终端聊天程序：斜杠命令 + 多会话管理。

### 任务
- [ ] REPL 打磨：/exit /new /switch /history 命令
- [ ] 会话命名与列表（扫描数据目录）；切换会话即切换历史
- [ ] 显示当前会话名与模型名；Ctrl+C 的优雅处理
- [ ] 测试：命令解析与分发；多会话隔离（A 会话的对话不进 B）

### 主要技术点
命令路由雏形（字符串→函数的分发表，为 16 课的 dispatch 直觉铺垫）；输入循环与异常；用户界面状态（当前会话指针）。

### 预计影响
新增 `nanobot_st/terminal.py`（main 入口）；`chat.py` 逐渐退居"引擎"角色。

### 与上一课的关系
前八课积累的能力（会话/工具/流式/容错）第一次组装成一个"产品"，也第一次出现"界面层 vs 引擎层"的分层。

### 完成标准
测试通过；能全程只用终端完成"开会话→问带工具的问题→切换→继续"。

## 第 10 课：读文件改文件——文件工具与工作区

### 背景
想让 AI 帮忙看代码、改文档。它现在只有 get_time/计算器，碰不到文件系统。

### 本课需求
read_file / list_dir / write_file / edit 工具，且只能碰指定工作区内的文件。

### 任务
- [ ] 四个文件工具（Tool 体系下新增即可——验证第 4 课的设计红利）
- [ ] workspace 概念：路径必须解析后落在工作区内（防 `../../` 逃逸）
- [ ] 大文件截断读取；edit 的"查找-替换"语义
- [ ] 测试：tmp_path 里建目录树，验证读/写/列/改与越界拒绝

### 主要技术点
pathlib 与路径安全（resolve + 相对判断）；文件 IO 的错误处理；工具输出截断（上下文保护，呼应第 6 课）。

### 预计影响

### 与上一课的关系
工具从"演示玩具"变成"生产力"；安全边界第一次成为需求。

### 完成标准
测试通过；真实让 AI 读一个文件并总结；越界路径被拒绝。

## 第 11 课：会跑命令的助手——shell 工具

### 背景
AI 能读能写，但不能跑测试、不能装依赖——改完代码还得我自己验证。

### 本课需求
exec 工具：执行 shell 命令，返回 stdout/stderr/退出码，带超时。

### 任务
- [ ] `asyncio.create_subprocess_exec` 执行与超时杀死
- [ ] 输出合并与截断；退出码语义（工具"失败"如何告知模型）
- [ ] 安全讨论：为什么原项目有 SSRF/工作区白名单；我们的最小防线
- [ ] 测试：echo/ls 成功；sleep 超时被杀；非零退出码被标为 error

### 主要技术点
子进程与异步等待；超时控制；"把错误当数据交给模型"的设计（ToolResult.is_error）；风险与最小权限直觉。

### 预计影响
`nanobot_st/tools/` 新增 exec；工具结果结构可能统一为带 is_error 的轻量结果。

### 与上一课的关系
文件工具给 AI 手，shell 工具给 AI 腿；两者合起来才是"干活的 agent"。

### 完成标准
测试通过；真实演示"让 AI 跑 pytest 并读输出修问题"的完整闭环。

## 第 12 课：分身有术——子代理

### 背景
让主助手去"通读整个目录并总结"，几十次工具调用的结果全灌进主对话，上下文爆炸，而且它只能串行干活。

### 本课需求
spawn 工具：主助手可以派出一个"分身"带着独立上下文去干脏活，只带结论回来。

### 任务
- [ ] spawn 工具：新消息列表 + 受限工具集 + 复用同一套工具循环
- [ ] `asyncio.gather` 并发派出多个分身；信号量限并发
- [ ] 分身结果以一条消息回注主对话
- [ ] 测试：FakeClient 模拟分身独立应答；验证主对话历史不含分身的中间过程

### 主要技术点
上下文隔离（为什么分身能防爆）；asyncio 并发原语（gather/Semaphore）；递归复用（循环引擎既服务主对话也服务分身）；（对照）原项目 SubagentManager。

### 预计影响
新增 `nanobot_st/subagent.py`；`chat.py` 完全成为可复用的"引擎"。

### 与上一课的关系
工具从"函数"升级为"另一个 agent"——组合爆炸的开始，也是架构收获期的开始。

### 完成标准
测试通过；真实演示并发两个分身各自总结两个目录；能解释"分身为什么必须有独立会话"。

## 第 13 课：记住我——长期记忆

### 背景
换个会话（甚至换个课的演示），它忘了"我偏好中文回复""我的项目在 ~/work"。会话记忆不等于用户记忆。

### 本课需求
跨会话的长期记忆：AI 能记住关于用户/世界的事实，并主动运用。

### 任务
- [ ] `MEMORY.md` 设计（一行一事实）；remember 工具（写入）
- [ ] 启动/每轮把记忆注入 system prompt（ContextBuilder 扩展）
- [ ] 记忆的读取链路：文件 → system → 模型引用
- [ ] 测试：remember 写入后，新会话的请求 system 里包含该事实
- [ ] （对照小节）原项目的三层记忆（MEMORY/SOUL/USER + history.jsonl + Dream 巩固）

### 主要技术点
文件作为最朴素的"数据库"；记忆注入的时机与格式；短期 vs 长期记忆的分界；（延伸）向量检索为什么暂时不需要。

### 预计影响
新增 `nanobot_st/memory.py` + remember 工具；ContextBuilder 注入点扩展。

### 与上一课的关系
第 5 课保存"对话"，本课保存"认知"——数据的所有权从会话转到用户。

### 完成标准
测试通过；新开会话说"记住我喜欢简洁回复"后，另一会话能体现该偏好。

## 第 15 课：服务化——HTTP API

### 背景
助手只能我在终端用。想写个网页、接个手机快捷指令、给同事调用——需要 HTTP 接口。

### 本课需求
把引擎包装成 OpenAI 兼容的 `/v1/chat/completions` 服务（支持流式 SSE）。

### 任务
- [ ] 选型 aiohttp（或届时对比标准库后定），实现 POST 路由
- [ ] 请求/响应格式对齐 OpenAI 规范（choices/usage 字段）
- [ ] 会话路由：用请求里的 session 字段或 model 字段映射到本地会话
- [ ] SSE 流式转发（引擎的增量回调 → HTTP chunk）
- [ ] （顺水推舟）引入极简 "总线" 概念：终端与 HTTP 都是引擎的"前端"
- [ ] 测试：fake 引擎下非流式与流式各一测；会话隔离一测

### 主要技术点
HTTP 服务基础（路由/状态码/JSON body）；SSE；长连接下的异步转发；（对照）原项目 MessageBus/渠道抽象的完整形态。

### 与上一课的关系

### 完成标准
测试通过；curl 调通非流式与流式；用任意 OpenAI 客户端库指向本服务能聊。

## 第 16 课：最后一道防线——Provider 抽象与 fallback

### 背景
一直只用 openai SDK 一家。现在：想用 Claude（原生协议不同）；且深夜主力模型挂了想要自动切换备用。

### 本课需求
支持第二家厂商 + 主备自动切换。

### 任务
- [ ] 引入 `LLMProvider` 抽象（chat 流式接口）——第二次大重构，由"第二种实现"倒逼
- [ ] 迁移现有 openai 调用为 `OpenAICompatProvider`；新增 `AnthropicProvider`（消息格式转换）
- [ ] `FallbackProvider` 包装：主失败且错误可切换 → 逐个试备用
- [ ] 测试：主挂从备成功；不可切换错误（如内容超长）不切换；两家 provider 消息格式各自正确

### 主要技术点
抽象接口与适配器（Anthropic↔OpenAI 消息互转是最好的教材）；组合/包装器（fallback 不改内部、只在外面套）；错误分类的复用（第 8 课投资在此回收）。

### 预计影响

### 与上一课的关系
课程闭环：从第 1 课"一个函数直连 API"到"面向接口的多厂商引擎"，学生亲历抽象的全部理由。

### 完成标准
测试通过；配置切换/故障切换均生效；能回答"为什么第 1 课不这么写"。
