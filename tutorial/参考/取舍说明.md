## 2. 简化后保留（保思想、弃工程完备性）

| 原项目存在 | 教学版本 | 理由 |
|---|---|---|
| turn 六阶段流水线 + 阶段计时日志 | 直线流程"取会话→组装→循环→保存→回复" | 六阶段是为崩溃恢复/压缩/命令路由服务的，没有这些需求时它只是噪音 |
| ContextGovernor 全套清洗（孤儿 tool 结果、畸形 tool_calls、占位剥离、字符预算 offload） | 仅"截断保最近 N 条 + 保持 tool 配对" | 清洗逻辑教学价值低；"截断不破坏配对"这个不变量必须讲 |
| 会话摘要压缩（Consolidator checkpoint + 水位） | 只讲概念，不实现 | 是原项目亮点但独立成一课会超纲；作为第 6 课的"业界做法"延伸阅读 |
| 重试矩阵（Retry-After、流恢复、空回复重试、length 续写） | 指数退避 + 可重试/不可重试二分 | 一个循环讲透模式，其余点到为止 |
| FallbackProvider + 熔断 + 半开探测 | 线性 fallback 链 | 包装器思想保住，熔断讲概念 |
| 流式分段（resuming/merge_next 语义） | 单段流式 | 分段是为多渠道卡片 UI 服务的 |
| MessageBus（双队列 + 订阅者 + 受众策略） | 第 15 课按服务化需求引入极简版 | 在 CLI 单渠道阶段引入总线=提前设计 |
| 技能系统（SKILL.md frontmatter/三层来源/渐进加载） | 不实现，第 13 课记忆处一句话对照 | 与记忆机制重叠度高 |
| Dream 记忆巩固（游标/受限工具/git 审计） | 不实现，讲设计故事 | 依赖 cron + git + 摘要三件事，超纲 |

## 3. 删除（不进课程，扩展课候选）

| 原项目存在 | 为什么删 |
|---|---|
| 161 个渠道适配文件（Telegram/Discord/Slack/邮件/Linear…） | 大量平台协议胶水与 OAuth；留 HTTP API 一条渠道即可覆盖"多渠道解耦"的教学点 |
| MCP 全套（mcp.py 1709 行 + OAuth + 重连） | 独立协议生态，值得单独课程 |
| OAuth providers（codex/grok/copilot/xai） | 平台专有流程 |
| WebUI 前后端（bun/react/websocket） | 前端工程，偏离 Python 后端教学主线 |
| gateway 进程管理 + systemd/LaunchAgent 安装 | 部署运维话题 |
| 崩溃 checkpoint / JSONL 损坏修复 / RecoveryAdmission | 多层兜底，教学价值低 |
| Windows 兼容（Job 对象、TUI native 构建） | 平台兼容代码 |
| llm_usage SQLite 统计 + 图表 | 独立小系统；SQLite 技能可在扩展课获得 |
| cron/triggers 自动化、goal/long_task | 依赖常驻进程+定时设施 |
| 配对（pairing）、音频转写、图像生成、插件市场 | 外围产品功能 |
| provider conversation_state / Responses API 续写 / 原生 compaction | 厂商专有高级特性 |
| LRU 会话缓存、filelock 跨进程锁、热重载 | 单进程教学版无此需求 |

## 4. 删除后的损失与补偿

- **真实感损失**：学生见不到生产级兜底 → 在相关课程（第 5/8 课）用"原项目怎么做"小节补偿，指认源码位置供自行阅读。
- **多渠道体验损失**：第 15 课后学生可自行尝试接 Telegram Bot API（用 requests 轮询即可），教案不覆盖。
- **长期记忆深度损失**：Dream/摘要不实现 → 第 13 课总结里给原项目 memory.py 的阅读路线图。

## 5. 结构性差异（允许且刻意）

- 教学项目包名 `nanobot_st`，目录扁平：`nanobot_st/` + `tests/`，按课逐个长出模块，**不预先建空目录**。
- 不复制原项目类名体系（如 TurnDelivery/AgentRunSpec/ProviderSnapshot），命名以教学清晰为先。
- 原项目全 async：教学项目第 1 课用同步（先专注消息格式与 TDD），第 2 课由"等待也是 IO"引出 async——这是一次刻意安排的认知台阶。
